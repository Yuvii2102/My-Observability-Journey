## 3. What is Observability?

Observability means understanding what is happening inside an application.

Imagine I have an online shopping application. Suddenly, customers are unable to make payments.

As a DevOps Engineer, I need to find out:

- Which service is having a problem?
- Why is the payment failing?
- How long are requests taking?
- Which service is causing the delay?

Observability helps me find answers to these questions.

There are three important parts of observability.

### 1. Metrics

Metrics are numbers that tell us how an application is performing.

Examples:

- CPU usage.
- Memory usage.
- Number of requests.
- Number of errors.
- Application response time.

**Simple example:** If my application is receiving 1,000 requests but 200 are failing, metrics help me understand the error rate.

### 2. Logs

Logs are messages generated by an application. They tell us what happened.

Examples:

- Application started.
- Database connection failed.
- Payment completed.
- User login failed.

**Simple example:** If a payment fails, I can check the application logs to understand what happened.

### 3. Traces

Traces show how a request travels between different microservices.

For example, when a customer purchases a product, the request may travel through:

```text
Frontend
   |
   v
Cart Service
   |
   v
Checkout Service
   |
   v
Payment Service
```

Traces help us understand which services handled the request and how much time each service took.

**Remember:**

- Metrics tell me how the application is performing.
- Logs tell me what happened.
- Traces show me where the request travelled.

## 4. Two Important Parts of Observability

My teacher explained that observability has two important parts.

### Part 1: Instrumentation

Instrumentation means making an application generate metrics, logs and traces.

This is mainly done by developers while writing the application code.

For example, if a developer creates a Payment Service, they need to add the required instrumentation so that the service can generate telemetry data.

As a DevOps Engineer, I should first check whether the application is already instrumented.

### Part 2: Implementing Observability

Once the application generates telemetry data, the DevOps or SRE team needs to collect and monitor it.

For this, we set up tools such as:

- OpenTelemetry.
- Prometheus.
- Grafana.
- Jaeger.

**Simple difference:**

Instrumentation means generating the data.

Implementing observability means collecting that data and making it useful for monitoring.

Both are important.

## 5. What is OpenTelemetry?

OpenTelemetry, also called OTel, is an open-source framework used to generate and collect application telemetry data.

It supports three types of data:

- Metrics.
- Logs.
- Traces.

### Why do we need OpenTelemetry?

Imagine a company uses Prometheus to monitor its applications.

Developers have written hundreds of microservices using Prometheus-specific libraries.

Now the company decides to move from Prometheus to another monitoring platform.

Developers may need to change the monitoring-related code in many microservices.

This takes a lot of time.

OpenTelemetry helps solve this problem.

Instead of writing code for one specific monitoring tool, developers use OpenTelemetry APIs and SDKs.

The generated data can then be sent to different observability tools using exporters.

For example:

- Metrics can be sent to Prometheus.
- Traces can be sent to Jaeger.

If the company changes its monitoring tool, it can often change the exporter configuration instead of modifying every microservice.

### Benefits of OpenTelemetry

1. It is open source.
2. It supports different programming languages.
3. It supports metrics, logs and traces.
4. It does not depend on one particular observability company.
5. It makes it easier to change observability tools.

**Remember:** OpenTelemetry provides a common way for applications to generate and send telemetry data to different monitoring tools.

## 6. How OpenTelemetry Works

OpenTelemetry has three important components:

1. Receiver.
2. Processor.
3. Exporter.

Let's understand them one by one.

### 1. Receiver

The receiver collects telemetry data from applications.

For example, it receives metrics, logs and traces generated by microservices.

### 2. Processor

The processor handles the collected data before sending it to the next component.

For example, it can filter or group the data.

### 3. Exporter

The exporter sends the processed data to the monitoring backend.

For example:

- Metrics can go to Prometheus.
- Traces can go to Jaeger.

### Simple Architecture

```text
       Microservices
             |
             v
       OpenTelemetry
             |
             v
          Receiver
             |
             v
          Processor
             |
             v
           Exporter
             |
       +-----+-----+
       |           |
       v           v
   Prometheus    Jaeger
    Metrics      Traces
       |           |
       v           v
    Grafana     Jaeger UI
```

The important thing is that OpenTelemetry collects and sends the data to the required tools.

## 7. How Jaeger Works

Jaeger is used to understand how requests travel between microservices.

In this project, OpenTelemetry generates the trace data and sends it to Jaeger.

Jaeger stores the trace information and provides a dashboard where I can view it.

### Example

Imagine I add a product to my shopping cart.

The request may travel through the Frontend and Cart Service.

Jaeger helps me see:

- Which services received the request.
- Which service called another service.
- How long each operation took.
- Whether any operation failed.

### What is a Span?

A span represents one operation performed while handling a request.

For example:

```text
Request
   |
   v
Frontend       - Span 1
   |
   v
Cart Service   - Span 2
   |
   v
Checkout       - Span 3
   |
   v
Payment        - Span 4
```

All related spans are grouped together in a trace.

This helps us understand the complete journey of a request.

## 8. How Prometheus Works

Prometheus is a monitoring tool used to collect and store metrics.

It stores metrics as time-series data, which means it keeps values along with their timestamps.

For example, it can collect:

- HTTP request count.
- Application response time.
- Error count.
- Application performance metrics.

In this project, Prometheus receives application metrics through the configured telemetry setup.

## 9. How Grafana Works

Grafana is used to display metrics in the form of graphs and dashboards.

It connects to Prometheus and displays the collected metrics in an easy-to-understand format.

For example, using Grafana, I can view:

- Application response time.
- Number of failed requests.
- Frontend latency.
- Application error rate.

The demo application already provides a dashboard.

I can also create my own dashboard and use PromQL to get the metrics I need.

### What is PromQL?

PromQL stands for Prometheus Query Language.

It is used to search and analyse metrics stored in Prometheus.

For example, my teacher demonstrated a metric called:

`http_server_duration_seconds_bucket`

This metric helps us understand HTTP request duration.

He also showed how to check the number of recommendations generated by the Recommendation Service.

## 10. Application Metrics vs Kubernetes Metrics

My teacher explained one important point.

The Prometheus instance included with this demo application does not collect all Kubernetes infrastructure metrics by default.

For example, it may not show:

- Kubernetes Pod information.
- Node CPU usage.
- Node memory usage.
- Kubernetes cluster resource information.

To collect these metrics, we need additional components.

### 1. Node Exporter

Node Exporter collects information about the machine running Kubernetes.

Examples:

- CPU usage.
- Memory usage.
- Disk usage.
- Network usage.

### 2. Kube-State-Metrics

Kube-State-Metrics provides information about Kubernetes resources.

Examples:

- Pods.
- Deployments.
- Services.
- ReplicaSets.

**Remember:**

Application metrics tell us how the application is performing.

Kubernetes metrics tell us how the Kubernetes cluster and its resources are performing.

We need the appropriate exporters to collect both types of information.

## 15. Complete Project Architecture

Now let's understand how all the tools work together.

```text
          User
           |
           v
     Demo Application
     (Microservices)
           |
           v
      OpenTelemetry
           |
      +----+----+
      |         |
      v         v
   Metrics    Traces
      |         |
```

### Simple Explanation

5. Grafana displays the metrics in dashboards.
6. Jaeger stores and displays the traces.

This gives us a complete view of application performance and request flow.
