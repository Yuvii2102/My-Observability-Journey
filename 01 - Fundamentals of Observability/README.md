# Day 1 – Fundamentals of Observability

## 1. What is Observability?

Observability is the ability to understand the internal state of a system by analyzing the information it generates.

In simple words, observability helps us understand what is happening inside our application, infrastructure and network.

Let's understand this with an example.

Imagine we have developed an application called **Resume Builder**. Users can register, log in, create resumes and download them.

We have deployed this application on a Kubernetes cluster running on AWS infrastructure.

Everything is working properly. But suddenly, users start reporting problems:

- The website is loading very slowly.
- Some users cannot log in.
- Some HTTP requests are failing.
- The application is consuming too much memory.

As a DevOps Engineer, we need to identify what is happening inside the system and find the reason behind these problems.

This is where observability comes into the picture.

Observability helps us answer three important questions:

### What, Why and How?

**1. What is happening?**

Observability helps us understand the current state of our system.

For example:
- CPU utilization is 95%.
- Memory utilization is 80%.
- Disk utilization is 90%.
- 50 HTTP requests are failing.

**2. Why is it happening?**

Observability helps us understand the reason behind the problem.

For example:
- CPU usage is high because one application is consuming too many resources.
- HTTP requests are failing because the database connection is not working.
- Memory usage is increasing because of a memory leak.

**3. How can we fix it?**

Observability provides information that helps us troubleshoot and identify the exact component causing the problem.

For example, we can trace an HTTP request from the load balancer to the frontend, backend and database to identify where the request is failing.

Therefore, observability helps us understand what is happening, why it is happening and how we can troubleshoot the problem.

## 2. Why Do We Need Observability?

Let's continue with our Resume Builder application.

Assume our application is deployed on a Kubernetes cluster with AWS infrastructure and proper networking.

Now we need to make sure that our application is working properly and providing a good experience to users.

But how do we know whether our application is healthy?

We need continuous information about our application and infrastructure.

Observability helps us collect information such as:

**Infrastructure information:**
- CPU utilization of Kubernetes nodes.
- Memory utilization.
- Disk utilization.
- Network traffic.
- Resource consumption.

**Application information:**
- Number of successful HTTP requests.
- Number of failed HTTP requests.
- Application errors.
- API response time.
- Application performance.

For example, if CPU utilization is constantly at 100%, our application may not perform properly.

Similarly, if CPU utilization is only 10% all the time, we might be wasting infrastructure resources and money.

Observability helps us understand these situations using historical information and detailed application data.

It also helps organizations identify problems before they become bigger issues.

## 3. Three Pillars of Observability

There are three main pillars of observability:

1. Metrics
2. Logs
3. Traces

These three pillars work together to provide complete information about our application and infrastructure.

### 3.1 Metrics

**What are Metrics?**

Metrics are numerical measurements collected over time that help us understand the performance and health of our system.

In simple words, metrics provide numerical information about our application and infrastructure.

Examples:

- CPU utilization: 80%
- Memory utilization: 65%
- Disk utilization: 90%
- Total HTTP requests: 1,000
- Failed HTTP requests: 50
- Application response time: 2 seconds

**Real-time Example:**

Imagine our Resume Builder application is running on a Kubernetes cluster.

We want to understand:
- What is the CPU utilization of a particular Kubernetes node?
- How much memory is being consumed?
- What is the disk utilization over the last 24 hours?
- How many HTTP requests are successful?
- How many HTTP requests are failing?

Metrics help us collect this historical information.

For example, CPU utilization might be normal throughout the day but suddenly increase to 100% at 10 AM.

Without historical metrics, it would be difficult to understand what happened at that particular time.

Metrics help us identify these changes and understand the performance of our system.

**Tool used for Metrics:**
- Prometheus

**Remember:** Metrics help us understand WHAT is happening in our system.

### 3.2 Logs

**What are Logs?**

Logs are records of events generated by an application or system.

In simple words, logs help us understand what happened inside our application and why a particular issue occurred.

Let's take an example.

A user tries to log in to our Resume Builder application, but the login fails.

Our application might generate the following logs:

```text
10:00:01 INFO User login request received

10:00:02 INFO Connecting to database

10:00:03 ERROR Database connection failed

10:00:03 ERROR Login failed
```

Now we can understand that the login failed because the database connection was unsuccessful.

There are different types of application logs:

| Log Type | Meaning |
|---|---|
| INFO | Normal application information |
| DEBUG | Detailed information for debugging |
| WARN | Something unusual happened |
| ERROR | An error occurred |
| TRACE | Very detailed diagnostic information |

Developers are responsible for writing proper logs inside their applications.

These logs help DevOps Engineers and developers troubleshoot application problems.

**Tools used for Logging:**

- Elasticsearch
- Fluent Bit
- Kibana

Together, these tools form the EFK Stack.

**Remember:** Logs help us understand WHY something happened.

### 3.3 Traces

**What are Traces?**

Traces help us understand the complete journey of an HTTP request through different components of an application.

This is also known as Distributed Tracing.

Let's continue with our Resume Builder example.

Imagine a user opens the application and clicks the Login button.

The request travels through different components:

```text
User / Client
      |
      v
Load Balancer
      |
      v
Frontend
      |
      v
Backend
      |
      v
Database
```

Now imagine the login request takes 10 seconds to complete.

We need to understand where the request is taking more time.

For example:

| Component | Time Taken |
|---|---:|
| Load Balancer | 10 ms |
| Frontend | 20 ms |
| Backend | 8 seconds |
| Database | 1.9 seconds |

From this information, we can understand that the backend is taking most of the time.

Traces help us understand:

- Where the request is going.
- Which component is processing the request.
- How much time each component takes.
- Where the request is failing.
- Whether the request is reaching the expected service.

This makes troubleshooting much easier in applications that contain multiple microservices.

**Tools used for Distributed Tracing:**

- OpenTelemetry
- Jaeger

**Remember:** Traces help us understand HOW a request travels through our application and WHERE it spends its time.

## 4. Understanding Metrics, Logs and Traces Together

Let's take one example.

Our Resume Builder application is experiencing slow performance and some HTTP requests are failing.

How will the three pillars help us?

**Metrics:**

We check Prometheus and identify that CPU utilization is 95% and 50 HTTP requests have failed.

This tells us WHAT is happening.

**Logs:**

We check the application logs using Kibana and identify that the backend is generating database connection errors.

This helps us understand WHY the requests are failing.

**Traces:**

We check the distributed traces using Jaeger and identify that requests are spending too much time in the backend and database.

This helps us understand WHERE the request is delayed and HOW it travels through the application.

Therefore, all three pillars work together to help us understand and troubleshoot application problems.

## 5. Difference Between Monitoring and Observability

Monitoring and observability are related, but they are not the same.

### What is Monitoring?

Monitoring is the process of continuously checking the health and performance of our application and infrastructure.

Monitoring mainly focuses on metrics, dashboards and alerts.

For example:

Imagine our application is running on an EC2 instance.

We configure an alert that says:

"If CPU utilization goes above 80%, send an alert to Slack or email."

We can also create dashboards using Grafana to visualize CPU, memory and disk utilization.

Monitoring helps us identify when something goes wrong.

### What is Observability?

Observability is a broader concept that helps us understand the internal state of our complete system.

It includes all three pillars:

1. Metrics
2. Logs
3. Traces

It helps us identify problems, investigate their root causes and troubleshoot them.

### Main Difference

| Monitoring | Observability |
|---|---|
| Mainly focuses on metrics | Includes metrics, logs and traces |
| Uses dashboards and alerts | Uses telemetry data to investigate problems |
| Helps identify when something is wrong | Helps investigate why something is wrong |
| Is a part of observability | Is a broader concept |

**Important:** Monitoring is a part of observability. Monitoring tells us when something is wrong, while observability helps us investigate why it is wrong.

## 6. Real-Time Company Use Case – Why Do Companies Need Observability?

Let's understand why organizations invest in observability.

Imagine we are working in a product-based company that has developed a Resume Builder application.

The application is deployed on a Kubernetes cluster running on AWS infrastructure.

Now the company wants to find customers and sell subscriptions for its product.

When a potential customer asks why they should choose our Resume Builder instead of other products in the market, our company can provide a Service Level Agreement (SLA).

### What is an SLA?

SLA stands for Service Level Agreement.

It is an agreement between a service provider and a customer that defines the expected level of service.

For example, our company promises:

- Our Resume Builder application will be available 99.9% of the time.
- 99.95% of requests will successfully respond within 30 milliseconds.

These are examples of service commitments made to customers.

But how can our organization make sure that we are meeting these commitments?

We need a continuous feedback system.

For example, assume we receive 10,000 HTTP requests.

If some requests start failing or taking more time than expected, we need to identify the problem immediately.

If three requests are failing, we should investigate the reason before the number increases further.

We need to understand:

- Are we meeting our SLA?
- How many requests are failing?
- Why are requests failing?
- Is the application becoming slow?
- Which component is causing the problem?
- How can we fix it before it affects more users?

This is where observability becomes important.

Observability provides continuous information about the internal state of our application and infrastructure.

It helps organizations identify problems early and maintain the expected service quality.

This is important for modern applications such as banking applications, e-commerce platforms, social media applications and other customer-facing services.

## 7. Is Observability the Responsibility of Developers or DevOps Engineers?

Observability is a collective responsibility.

Both developers and DevOps Engineers have important roles.

Let's understand their responsibilities.

### Developers' Responsibilities

Developers work on the application code.

They are responsible for:

- Writing proper application logs.
- Instrumenting custom application metrics.
- Implementing distributed tracing.
- Adding OpenTelemetry instrumentation where required.

For example, developers write code that generates information about application errors, API requests and performance.

### DevOps Engineers' Responsibilities

DevOps Engineers are responsible for setting up and maintaining the observability platforms.

They work on:

- Setting up Prometheus for metrics collection.
- Configuring Grafana dashboards.
- Setting up Alertmanager for alerts.
- Deploying the EFK stack for logging.
- Setting up Jaeger for distributed tracing.
- Configuring and maintaining the observability infrastructure.

For example, developers generate application metrics, but DevOps Engineers configure Prometheus to collect and monitor those metrics.

Similarly, developers generate application logs, while DevOps Engineers set up the logging platform to collect, store and visualize them.

Therefore, observability requires collaboration between developers, DevOps Engineers and SRE Engineers.

## 8. What is OpenTelemetry?

OpenTelemetry is an open-source observability framework.

It provides a collection of APIs, SDKs and tools that help developers instrument applications to generate and collect telemetry data.

It supports the three pillars:

- Metrics
- Logs
- Traces

Developers can use OpenTelemetry to add instrumentation to their applications.

This information can then be sent to observability platforms for monitoring, logging and tracing.

OpenTelemetry is not a single monitoring tool. It is a collection of APIs and SDKs that help generate and collect telemetry data.

We will learn more about OpenTelemetry and its practical implementation during the distributed tracing part of this series.
